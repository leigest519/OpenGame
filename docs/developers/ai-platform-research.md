# OpenGame 模块化游戏平台架构与实施路线

核验日期：2026-10-13。用户确认的目标为「AI 生成小游戏，在线试玩、修改和分享」。本地分析基于提交 `c9bea37`，并结合官方部署文档。以下区分源码事实、外部文档事实与实施判断；本次没有部署服务或运行模型生成任务。当前工作区未安装 `node_modules`，因此尚未验证安装、构建、生成成功率、耗时或成本。

页面行为、模块职责、任务恢复、版本一致性、数字币订单关联与逐项验收已整理为[首版产品与实施规格](ai-platform-mvp-spec.md)。本文保留源码依据、架构选择与后续路线；开始开发时结合两份文档使用。

## 已确认的产品方向

- 用户描述玩法、在线试玩、对话修改和分享，不需要选择模型。第一版只接 Codex 执行器，优先使用现有订阅做本地验证；Gemini 和其他模型保留后续接入空间，CC Switch 不作为必需依赖。
- 每个游戏项目拥有独立私有 Git 仓库和项目记忆。游戏版本绑定代码、设计文档、记忆摘要、模块依赖和素材引用；聊天历史独立保存。
- 游戏结构由需求决定。公共模块用于加速开发，不以五种游戏类型或既有玩法模板限制生成；缺少能力时允许开发项目内模块和原创玩法代码。
- 所有项目共同改进一套平台公共游戏开发规范。每次开发、修改、验收和修复都可以贡献经过归纳的经验；候选改进经过验证后发布，供所有开发者后续的适用任务使用。公共规范、公共模块和私有项目记忆分别管理。
- 第一阶段游戏在自有平台运行、试玩和分享。Steam、Roblox、微信小游戏及其他平台作为后续运行与发布目标，逐个增加适配和发布能力；平台负责简化准备、打包、检查、上传与状态跟踪。
- 支付优先服务海外玩家购买游戏或游戏内商品，先接入自有平台，首期只使用数字货币付款。开发者付费使用生成服务不作为首个支付场景。国家与地区暂不作为当前架构讨论的前置条件；具体币种、网络与收款实现待验证，正式收款前另行核实适用规则。
- 能力范围逐步验证。首轮利用现有 Phaser 工程验收浏览器 2D 游戏，不把 2D 或具体玩法写死在平台数据结构中。3D、联机、其他运行环境需要相应实现与验收，不能仅凭模块化设计宣称已经支持。

## 模块组织与生成流程

### 根据能力组合游戏

用户需求 → 玩法设计与能力清单 → 确认目标运行环境（首版为浏览器）→ 检索兼容模块与适用的公共规范 → 创建最小启动工程 → 组合模块并编写原创玩法 → 构建与试玩验收 → 保存项目版本并提交经验候选。

能力清单描述输入设备、空间与运动方式、时间推进、交互规则、资源需求、是否联网及验收条件，不要求先选一个游戏类型。类型标签可用于检索和展示，不能成为生成的前置条件。最小启动工程仅解决启动、构建、资源路径和运行循环，不预设角色、战斗或胜负规则。

例如，“通过抽卡控制飞船迎击敌人”可以组合卡牌、移动、波次、伤害和界面模块，再编写卡牌如何影响飞船的项目玩法。没有兼容模块时直接实现所需能力，项目不因模块库缺项而被强制改成已有玩法。

### 模块的四种职责

| 层次           | 职责                                               | 复用方式                                                                                           |
| -------------- | -------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 运行环境       | 启动、渲染、输入、时间、资源加载、音频             | 第一轮实现 Phaser 所需能力；出现真实的第二种运行环境时，再为共同接口增加适配器。                   |
| 通用玩法模块   | 卡牌、回合、波次、伤害、物品、任务等               | 每个模块提供少量明确接口，隐藏内部实现，不依赖某个游戏的角色名或场景类。仅实现实际需求涉及的模块。 |
| 项目玩法       | 规则组合、角色技能、关卡目标、特殊交互             | 允许原创代码，保存在项目私有仓库；不要求所有玩法都先变成公共模块。                                 |
| 制作与验证规范 | 素材一致性、模块生命周期、状态保存、构建与试玩检查 | 按本次能力需求加载，约束正确性和可维护性，不限制玩法创造。                                         |

纯玩法逻辑尽量与渲染分开；依赖物理、相机或特定引擎的模块明确标注兼容范围。不会把 2D 物理代码仅改接口名称就宣称可用于 3D。也不预先设计所有引擎通用的巨大接口。

### 一个模块需要交付什么

- **用途和范围**：提供的能力、适用情况、不适用情况，以及依赖的引擎和其他模块。
- **稳定接口**：输入输出、配置、事件及其顺序、初始化与销毁、状态所有权、错误行为。模块有时间循环或存档需求时，额外定义更新时间单位与状态保存方式。
- **实现与版本**：可运行代码、准确版本、依赖约束和来源；项目锁定模块版本与内容校验值。
- **最小示例与验收**：可独立运行的使用示例、通过公开接口进行的行为验证，以及与其他模块组合的验收样例。

模块只暴露完成任务所需的接口，不直接读取其他模块的内部状态，不依赖一个包含整个游戏的全局对象。相互通信优先使用明确调用和声明过的事件，不把所有交互塞进无类型的全局事件通道。项目只加载实际使用的模块及文档。

第一版用仓库内模块目录和清单管理即可，不需要先做插件市场或为每个模块部署独立进程。公共模块采用固定版本；项目可以创建本地修改版，并在模块清单中记录来源及变更，后续更新不会覆盖这些修改。

### 主流程需要改变的地方

1. [分类工具](../../packages/core/src/tools/game-type-classifier.ts) 的固定五类枚举不再作为平台入口。新增能力分析，输出需求、可复用模块、缺失能力和验证方案。
2. [设计文档生成](../../packages/core/src/tools/generate-gdd.ts) 当前要求 archetype，并据此选规范。改为读取能力清单和所选模块接口，允许自由组合与新的运行环境需求。
3. [制作规范](../../agent-test/docs/gdd/core.md) 和 [代理提示词](../../agent-test/prompts/custom.md) 中“只能复制模板”“禁止新行为”等约束需要改为“优先复用；不足时允许新增模块或原创实现”。保留真实接口、素材清单、生命周期清理与测试要求。
4. 第一版通过同一个 Codex 执行入口完成需求分析和代码修改。现有 GDD、素材与进化工具中独立的 API 调用仍需分别适配；不会因已有 Codex 订阅就自动可用。先使用固定素材验证生成流程。

## 公共游戏开发规范

公共规范是平台共同维护、带版本记录的开发资产。所有游戏的创建、修改、验收、修复和开发者反馈都进入经验采集流程，既记录成功做法，也记录失败原因与效果尚未确认的尝试。贡献的是可复用的开发经验；项目源码、完整聊天、角色剧情和私有素材继续留在项目内。共享验证样例使用最小复现或合成数据，并保留来源与使用范围。

| 资产         | 保存什么                                                                 | 谁使用                                           |
| ------------ | ------------------------------------------------------------------------ | ------------------------------------------------ |
| 公共开发规范 | 需求拆解、模块接口、资源与状态管理、输入适配、性能、验证和发布的可靠做法 | 所有开发者的适用任务，按运行环境与能力需求加载。 |
| 公共模块库   | 已验证的可复用代码、接口、示例和依赖版本                                 | 需要该能力且满足兼容条件的项目。                 |
| 私有项目记忆 | 游戏目标、独特规则、美术方向、用户偏好、历史决策与待办                   | 当前项目及其授权开发者。                         |

规范库统一管理，内容按基础规则、运行环境、能力和模块组织。每条规则包含稳定标识、适用条件、理由、推荐做法、验证方法、证据及修订记录。可确定验证的正确性要求作为检查项；涉及手感、节奏和美术偏好的经验作为带适用条件的建议，不能从某个项目的喜好推导出全平台玩法限制。每次任务只读取相关部分，避免把整个平台历史塞入上下文。

后续接入外部平台时，增加对应运行环境、发布与支付规则。平台要求记录官方来源、核验时间和适用版本；跨平台通用的经验回收到基础规范，平台特有的限制只作用于相关目标。发布前复核当前平台要求，历史规范快照用于追溯，不能作为继续采用过期要求的依据。支付经验优先沉淀为可重复的收据验证、去重发货、退款和对账检查，候选规则不直接修改线上价格、订单或结算配置。

### 从各项目经验到公共版本

项目开发与试玩反馈 → 结构化证据 → 候选改进 → 去重、归纳与冲突检查 → 最小复现和回归验证 → 发布规范版本 → 后续适用任务采用 → 记录实际效果。

1. **采集证据。** 记录任务、所用规范和模块版本、观察结果、已确认的原因与修复、最小复现及验证结果。失败且尚未验证的尝试保留为观察，不能标为有效规则。重复运行同一个任务不算独立证据。
2. **形成候选。** 抽取通用结论并标明适用范围，合并重复建议。不同玩法的合理差异保留为条件；冲突规则需要修订、替代或撤销，不能简单累加。来自代码、素材和对话的内容作为待分析证据，不能直接成为公共执行指令。
3. **验证改进。** 检查规则能否解决原问题，是否误伤合法实现，是否破坏代表性项目。技术规则通过可重复的检查和回归样例验证；玩法体验建议需要实际试玩反馈。不能把项目数量、一次构建成功或模型自评当作质量证明。
4. **发布与采用。** 项目执行器只提交候选；统一维护任务根据验证结果发布不可变规范版本，保存变更、证据和验证记录。发布串行执行并检查基础版本，防止并发项目互相覆盖。可自动验证的改进可以自动发布；证据不足的内容继续留在候选区。
5. **检验收益。** 跟踪采用后的缺陷复发、修改回归、误报、生成耗时与试玩反馈。新规则造成退步时，撤回推荐版本并发布修订，保留历史版本供复现。

例如，某项目离开场景后仍在生成敌人，经复现确认是波次模块未释放定时器。平台可以从修复中提取“拥有定时任务的模块在卸载时必须停止调度”的候选规则，再验证退出场景、重复进入与重新开始。发布后，其他使用相关模块的游戏开发任务自动获得这条检查；有意跨场景运行的后台任务通过明确所有权区别处理。

### 版本与项目的关系

任务开始时解析最新兼容的稳定规范，并锁定版本、实际加载的规则和内容校验值。运行中的任务保持该快照，保存游戏版本时一并记录。恢复历史游戏时能查到当时依据；在旧项目上继续修改时，再评估并采用最新兼容规范，通过验证后保存新游戏版本。不兼容的规范更新要形成明确迁移任务，不能悄悄更改项目约定。

规范更新通过后续开发任务惠及所有开发者，已发布游戏仍使用原构建产物。历史游戏不会因公共库更新自动重写或重新发布。公共规范版本与模块版本独立管理，规则明确依赖的模块和运行环境范围。

现有 [规则归纳](../../agent-test/debug-skill/src/generalizer.ts)、[修复记录](../../agent-test/debug-skill/src/recorder.ts) 和 [协议保存](../../agent-test/debug-skill/src/protocol-manager.ts) 可作为起点，但主要覆盖调试经验，尚缺完整制作规范、候选与稳定版本的发布隔离、并发控制、回归门槛和主流程接入。这些能力均属于待实现工作。

## 公共模块如何进化

项目内实现与验收 → 出现真实复用需求 → 提取候选模块 → 验证接口与不同组合 → 发布公共模块版本 → 适用项目采用并反馈。

候选模块去除项目角色、剧情和私有数据，仅使用允许贡献到公共库的内容。模块至少具备接口验证和可运行示例；声称跨玩法通用时，需要在不同玩法组合中验证。公共规范为模块抽取和验收提供要求，模块使用中发现的问题再贡献给规范库。

项目锁定模块版本。升级在项目的新工作区内完成，验证通过后生成新 Git 提交，失败保留原版本。规范与模块的持续改进发生在外部知识和代码层，不依赖更新模型权重。模块提取、验收、发布和主生成流程的接线均属于待实现工作。

## 项目仓库与记忆

每个项目的 Git 提交一起保存源码、游戏设计、记忆摘要、模块锁定清单、公共规范版本与规则清单、素材引用。完整聊天、任务日志及版本索引保存在业务数据库，大素材、构建产物和仓库备份保存在文件存储中，均按用户与项目隔离。

任务从明确的基础提交创建独立工作区，加载对应记忆与相关对话。验收后写入候选提交、保存不可变产物并登记版本；同一项目的修改串行执行，完成时检查基础版本与执行代次，避免较晚完成的任务覆盖新改动。Git、产物存储与数据库不共享事务，先保存待完成记录，确认源码和产物完整后再更新最近可玩版本；保存中断可恢复，不重新生成。任务失败保留日志与待检查修改。回退通过基于旧版继续创作保留历史，聊天记录不随游戏回退删除。

版本引用同时记录源码提交、模块清单、公共规范快照、素材清单和构建产物。自有平台的试玩版本与公开发布版本分别指向已通过验收的结果；继续编辑不会覆盖公开游戏。后续各发布目标分别关联自己的构建产物和上线版本，某个平台的适配或发布失败不改变其他平台的已发布版本。项目仓库由平台私有管理，连接 GitHub 属于可选导出能力。

## 多平台运行与发布路线

第一阶段完整实现自有平台的生成、试玩、修改、保存版本和链接分享。创作工作台继续采用试玩优先布局，发布入口只展示已经可用的自有平台能力。外部平台在后续逐个接入，接入顺序依据开发者需求与实际适配成本决定。

### 各目标需要解决的问题

下表为实施路线，外部平台适配均尚未实现。

| 目标       | 游戏运行与验证                                                                           | 简化的发布工作                                                             |
| ---------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 自有平台   | 首版浏览器游戏，验证资源加载、主要交互、重新开始和目标设备表现                           | 保存不可变产物，选择上线版本，生成试玩与分享链接。                         |
| Steam      | 准备目标桌面系统的可运行游戏包；浏览器项目评估桌面封装与平台功能适配，再进行实际运行验证 | 准备商店资料与构建配置，上传构建，衔接审核、上线和更新流程。               |
| 微信小游戏 | 准备小游戏工程，适配输入、资源、存档与所用平台能力，通过开发者工具和真机验证             | 自动准备工程与发布资料，生成预览、上传版本；提交和上线按实际开放能力接入。 |
| Roblox     | 生成相应场景、Luau 代码与客户端／服务端实现，在 Roblox 环境验证                          | 准备游戏资料、更新目标 place、跟踪发布结果；逐步接入可用的官方工具。       |
| 其他平台   | 登记运行要求、支持能力、产物格式及验收方式，完成代表性游戏验证后开放                     | 复用已验证的发布步骤，补充该平台所需的配置与操作。                         |

**已核实的平台事实：** SteamPipe 支持构建上传，并需要配置应用、内容 depot 和启动方式；正式上线还包含商店页面与构建的审核、发布步骤。[Steam 构建上传](https://partner.steamgames.com/doc/sdk/uploading)，[Steam 发布流程](https://partner.steamgames.com/doc/store/releasing)。微信官方 `miniprogram-ci` 支持 `miniGame` 项目类型、预览与上传，可作为发布自动化的起点；这些功能不能单独证明审核和正式上线也能由同一工具自动完成。[微信官方 CI 文档](https://github.com/wechat-miniprogram/miniprogram-ci-dist/blob/master/README.md)。Roblox Studio 使用 Luau，并围绕游戏与 place 组织发布。[Roblox Luau](https://create.roblox.com/docs/luau)，[Roblox 发布文档](https://create.roblox.com/docs/production/publishing/publish-games-and-places)。

### 运行环境与发布目标分别管理

游戏项目保留统一的玩法设计、独立 Git 仓库和项目记忆。运行环境回答“游戏代码在哪里、如何执行”，发布目标回答“产物交给谁、怎样上线”。同一种运行环境可以面向多个发布目标；Steam、微信和 Roblox 对运行方式与工程格式的要求需要分别处理。

基于当前浏览器实现路线的判断：Roblox 应作为独立生成与验证目标，需要对应代码和场景实现。可复用的部分包括玩法设计、数据、规范、模块契约和格式及使用范围允许的素材；每个公共模块明确声明已有的运行环境实现。不能把网页构建包直接标为 Roblox 游戏，也不能假定网页验收已经覆盖微信或桌面运行效果。

后续创建项目时，如果开发者已经指定外部目标，就从需求规划阶段加载该目标的能力与规范。已有项目新增目标时先给出兼容性结果和适配工作，再创建目标实现；无法直接复用的模块允许新增对应实现。不同目标的实现可以保存在同一项目仓库的不同目录，并保存各自的决策摘要，不要求为每个平台另建一个游戏项目。外部目标的试玩入口可以打开相应客户端或预览工具。

### 统一的发布体验

选择游戏版本与目标 → 检查兼容性和必需资料 → 完成必要适配 → 构建与目标环境验收 → 预览发布资料 → 按已授权操作上传或提交 → 跟踪结果并返回游玩入口。

发布模块向用户说明当前能执行到哪一步、需要补充什么、下一步是什么。它可以自动整理版本说明、截图、封面与平台所需资料，复用开发者已经完成的账号配置；正式操作依据该目标的可用工具与授权范围执行。账户配置、平台审核与必要的人工操作在流程中明确呈现，不承诺所有平台都能无需介入即时上线。外部账号授权由发布模块使用，不进入游戏源码或生成任务上下文。

构建完成、上传成功、审核通过和正式上线分别记录。发布任务保存平台返回的标识与原始状态；未知结果先查询再决定是否重试，避免重复提交。每个目标单独记录发布版本和入口，只有确认正式生效才显示“已上线”。支持回退时按平台能力执行；不支持时保留历史产物并走新的发布流程。

### 第一版保留的扩展位置

- 游戏版本记录运行环境；发布记录单独保存目标、来源版本、构建产物、状态与游玩入口。首版只有自有平台目标。
- 通用玩法逻辑通过实际需要的输入、存档、资源等接口使用环境能力，模块清单注明兼容范围。先落实当前模块所需的接口，再根据第二种运行环境调整。
- 自有平台发布流程先封装在 worker 内。出现第二种实际发布实现后，再提取共同的发布接口与平台适配器，不提前建设完整插件市场或所有平台的 SDK 层。

## 海外玩家支付与开发者收益

首个商业场景是海外玩家在自有平台使用数字货币购买游戏或游戏内商品。支付模块连接商品、链上收款、权益和开发者收益；游戏生成流程只集成经过验证的购买接口。首期不接银行卡或法币兑换。以下为设计方案，尚未创建收款钱包、接入真实支付或发生资金交易。用户暂缓国家与地区的选择，技术设计与测试网验证可以先行；主网真实收款前仍需按实际运营情况核实适用规则和所用服务的条件。

### 首轮商品与购买体验

首轮先验证游戏买断和永久权益，例如完整游戏访问权、额外关卡、角色或皮肤。消耗型道具在服务端库存与消耗记录完成后接入。商品价格、购买后得到的内容及退款规则由开发者在发布设置中明确，玩家在付款前看到相同内容。先用一个游戏、少量固定商品和一种计价币种完成验收，具体价格和平台分成比例另行确定。

玩家选择商品 → 平台创建订单 → 钱包确认付款 → 后台核验链上到账与订单归属 → 自动解锁游戏或发放权益 → 展示订单与到账结果。

玩家关闭页面或暂时离线后，确认收款与发货仍可继续；再次登录可以恢复已购权益。游戏内购买复用平台可信购买界面，生成的游戏只能请求购买与查询授权范围内的权益，不能提交自定成交价格或直接标记订单已支付。付费游戏访问与关键权益由服务端校验，单纯隐藏按钮或在浏览器存档中设置标记不能作为付费保护。

### 数字货币单通道

首轮采用一个稳定币和一个网络，减少钱包操作、错链与对账复杂度。技术候选为原生 USDC 与 Base，先在 Base Sepolia 测试网验证。Circle 官方列有 Base 主网与 Base Sepolia 的 USDC 合约，并明确测试网代币没有真实金融价值；主网和测试网配置必须分开。[Circle USDC 合约与测试网络](https://developers.circle.com/stablecoins/usdc-contract-addresses)。这一候选尚不等于用户已选定币种；USDT 或其他网络按后续实际需求接入。

技术验证优先采用卖方钱包直收、平台只读核验到账的结构，不以银行结算或 Stripe 商户开通作为开发依赖。付款界面明确显示代币、网络、金额、收款方和预计网络费；钱包签名在玩家的钱包内完成，平台不接收玩家助记词或私钥。使用成熟钱包连接能力，订单与发货仍由平台服务端管理。没有对应钱包或资产的玩家，首期不内置兑换与购币功能。

每份支付请求锁定订单、玩家、卖方、网络、代币合约、应付金额、有效期与收款地址，金额使用代币最小单位计算。首轮优先验证订单绑定唯一付款授权的方案，采用指定网络、合约、付款钱包与 nonce 关联订单；目标合约与钱包兼容性需实际验证，通过后才能接入。不能只按公共收款地址和相同金额猜测订单归属。付款人提交的交易哈希仅作为查询线索；后台还须核验链、代币、转账结果、收款方、金额、订单关联和该笔支付是否已被使用。具体候选协议、过期处理和发货约束见[首版支付规格](ai-platform-mvp-spec.md#数字货币购买闭环)。

支付状态区分待付款、已发现交易、确认中、已支付和异常。按目标网络经过验证的确认策略发货，处理链重组、查询中断、迟到付款、少付、多付及错链。支付索引可断点续查，重复扫描或任务重试不能重复发货；后台金额计算也不依赖代币名称或浏览器展示值。

第一轮无需新发代币或把游戏道具转换为链上资产。稳定币承担付款功能，游戏购买权、库存和游戏状态保存在平台业务系统中。游戏生成代理不自行编写收款或资金分账合约；后续若需要链上合约，由独立支付模块选择成熟方案并单独验证。

### 公共交易模块

| 职责       | 服务端负责的内容                                                                                           |
| ---------- | ---------------------------------------------------------------------------------------------------------- |
| 商品与订单 | 保存所属游戏、卖方、商品、玩家、价格、代币、网络及收款地址快照，核对当前可售状态；价格由可信商品目录确定。 |
| 支付确认   | 核验链上结果和确认程度，匹配订单、收款方、金额与代币合约，保存交易及事件标识并阻止重复使用。               |
| 权益与发货 | 根据已支付订单授予游戏访问权、永久权益或物品，记录唯一发货凭证；重复通知不会重复发货。                     |
| 退款与对账 | 分别记录收款、发货、退款申请与退款到账，保留更正记录；按商品规则处理权益撤回，核对链上流水。               |
| 开发者收益 | 按币种记录销售额、退款、相关费用和服务费约定；区分卖方实际到账、待处理款项与应付服务费。                   |

实施时将已经核验的付款记录和持久化发货任务纳入同一次数据库事务，链上付款本身不属于该数据库事务。按网络、交易和事件建立支付去重约束，发货按订单及商品建立唯一约束并可重试。监听通知仅触发复查，钱包返回成功只用于展示进度；以服务端核验结果推进订单。支付成功后发货失败保留待补发状态，不要求玩家再付一次。

玩家库存和订单历史不随游戏代码版本回退而回退。道具或权益需要稳定标识，游戏更新时兼容既有购买；撤回或迁移权益按已公示商品规则处理。公共支付模块通过服务端控制实际权益，游戏内效果按各运行环境实现。

### 开发者直收与退款

首轮按卖方直收设计：自营游戏由运营方钱包收款，第三方游戏后续由相应开发者绑定并验证收款钱包。订单创建后固定收款地址；开发者更换地址只影响后续订单。平台记录并核对销售与权益，不默认把所有开发者收入归集到一个平台钱包。

退款是由收款方发起的新付款，需要确认退到哪个经过验证的钱包、退还金额和网络费承担规则；数据库标记“已退款”不会令链上资金自动退回。平台保存申请、付款授权和退款交易，核验到账后再更新完成状态。玩家退款地址不能仅凭聊天消息或一张转账截图更改。

平台分成先定义账务规则和验证计算，实际收费比例待定。卖方直收模式下，平台不会自动获得订单中的服务费；若要自动分账，需要另行实现并验证对应协议。开发者看到的销售记录、实际钱包到账和已结算服务费必须分开。数字货币付款、卖方直收和平台分成分别验收，避免把收入统计误当作资金结算。

### 外部平台支付与首轮验收

后续发布到外部平台时，商品可映射为各平台商品标识，付款和收据验证按平台规则接入。Steam 的游戏内购买要求使用其微交易接口与 Steam Wallet；Roblox 开发者商品通过其购买流程，并由服务端处理购买收据。[Steam 游戏内支付](https://partner.steamgames.com/doc/features/microtransactions)，[Roblox 开发者商品](https://create.roblox.com/docs/production/monetization/developer-products)。微信小游戏支付在对应发布目标实施时核验可用能力。自有平台的稳定币选项不会自动出现在这些平台的游戏内，跨平台权益共享也需要单独确认并实现。

首轮在测试网覆盖成功付款、钱包拒绝、交易失败、延迟确认、重复扫描、旧交易冒领、错币错链、迟到或不足额付款、付款后离线、发货失败重试、换设备恢复权益及退款。完成链上付款与订单归属验证后，再评估主网启用；测试代币与真实资产分开，主网收款地址不得由生成代理猜测或自动替换。运营地区暂缓选择不阻塞测试网工作，真实运营前再落实适用规则。开发者生成服务收费可在此基础上另行设计，不与玩家游戏商品共用余额或商品目录。

## 接入时优先处理的实际问题

1. **把能力规划与执行准备封装起来。** 仅调用 `query()` 不等于复现 Game Skill，也不等于接入 Codex。显式加载新的模块化制作规范、所选模块接口和项目上下文；平台确定性创建最小启动工程并解析依赖，不再复制整套玩法模板。
2. **把新建与修改分开。** 现有专用提示词从分类和复制模板开始，直接用于修改可能造成重建。修改任务应恢复指定版本源码、设计文档和素材，再注入编辑目标与变更摘要；参数变化优先改 `gameConfig.json`，素材没有变化就复用。每次成功保存新版本，失败保留上一可玩版本。
3. **不能把 SDK 会话当作持久版本。** 当前 `Query` 构造时生成新 session ID，传输参数未暴露 `resume`。CLI 本身有恢复机制，但需要另行接入。MVP 可以通过源码快照、需求摘要和对话记录恢复编辑上下文，不依赖常驻会话，也不把沙箱一直保留到用户下次编辑。
4. **把生成与构建放进隔离环境。** SDK 会合并宿主 `process.env` 后启动子进程，测试入口使用 `yolo`。不要在带平台管理凭证的 Web API 进程内直接执行用户生成任务。沙箱使用独立工作目录、最小凭证和明确时限；模型调用凭证也需要额度限制或任务级代理。
5. **补充浏览器质量门槛。** 测试入口的成功条件主要是 SDK 返回 success，不能据此显示“游戏可玩”。README 还注明 OpenGame-Bench 评测流水线尚待发布。应独立检查构建产物、页面加载、资源错误、控制台异常、开始按钮、主要输入和重新开始，再决定是否提供可分享版本。
6. **把运行资源纳入发布镜像。** 当前 SDK 打包脚本复制 CLI/vendor/locales，Dockerfile 的运行层没有复制 `agent-test` 游戏模板与文档，也没有安装 Chromium/ffmpeg。需要制作并验证适合游戏平台的镜像；视频/音频能力若启用，还要满足相应外部依赖。

## 分阶段部署架构

本地验证采用 **网页工作台 + 持久化任务 + 独立 Node worker + Codex 执行器 + 每项目 Git 仓库与记忆 + 公共模块库与开发规范 + 游戏运行环境**。第一版生成并发设为 1，先面向本人受信任的开发任务。每个任务使用独立工作区和明确的执行权限；工作目录分开本身不等于安全沙箱。

浏览器提交需求后，后台检查项目权限并创建任务；worker 恢复基础版本，加载模块、适用规范和项目记忆，调用 Codex 生成或修改，再执行构建与浏览器验收。成功后保存 Git 提交与不可变产物，登记新的可玩版本。任务结束后异步提交经验候选，规范维护复用同一执行队列，不阻塞用户试玩，也不必先部署多个模型服务。用户选择发布时更新公开版本引用。页面通过任务事件或轮询显示进度。

面向公网阶段需要服务端生成接入、额度控制及可验证的任务隔离。**Next.js + Supabase Auth/Postgres/Storage/Queues + E2B + 独立游戏静态域名** 保留为部署候选。下列官方能力说明用于评估该阶段，不表示这些外部服务已经配置，也不作为本地验证的前置条件。

## 公网部署参考

### 网页 API 与生成任务分离

**官方事实：** Next.js 支持通过 Route Handlers 提供 API，但文档明确指出：部分托管环境会把它部署为 lambda；此时跨请求不能共享内存状态，文件系统能力可能受限，长请求可能被超时终止。这是部署环境约束，并非所有 Node 服务都不能执行长任务。[Next.js：Backend for Frontend](https://nextjs.org/docs/app/guides/backend-for-frontend#deployment-environment)

**实施判断：** 不把完整生成、依赖安装、构建、浏览器调试绑在一次 HTTP 请求里。云端可使用 Supabase Queues 与一个常驻 worker，另用任务表保存业务状态；领取任务需要配置可见性窗口、续租/心跳、重试次数和幂等键。状态至少包含 `queued/running/succeeded/failed/cancelled`；页面关闭后任务仍可继续，worker 重启后可识别失联任务。不能把队列投递保证当作模型调用、发布、扣费自动只发生一次。

**官方事实：** Supabase Queues 基于 Postgres 的 `pgmq`，提供持久消息和可配置的可见性窗口。若选择 Supabase，可复用其数据平台，减少额外队列服务。[Supabase Queues](https://supabase.com/docs/guides/queues)

### Supabase 的账户与数据能力

**官方事实：** Supabase 提供完整 Postgres、邮件/社交登录、基于 Postgres RLS 的授权、文件存储、自动 REST API 和 JavaScript 客户端。[Supabase 功能目录](https://supabase.com/features)

**官方事实：** Storage 使用 `storage.objects` 上的 RLS 控制访问；默认没有允许策略时不能上传。`service key` 可以绕过 RLS，官方明确要求不要公开。[Supabase：Storage Access Control](https://supabase.com/docs/guides/storage/security/access-control)

**实施判断：** 首批表只需要项目、版本、生成任务、任务事件和用量记录；每条私有记录绑定用户 ID。Storage 保存源码包、图片和构建文件；对外运行游戏另接独立静态域名或发布网关，并验证 HTML/JS 的响应类型、资源路径与安全响应头，不能把「能存文件」直接等同于「已具备游戏平台发布」。服务端管理密钥仅留在可信服务，生成代码和浏览器都不应拿到它。

### E2B 的执行与浏览器验收能力

**官方事实：** E2B 官方 cookbook 有 Node 20 基础镜像的 Playwright/Chromium 示例，演示了沙箱中的命令执行、浏览器访问、截图及产物复制。该示例明确说明它依赖专用镜像与浏览器配置，不能直接替换成默认 code-interpreter 基础镜像。[E2B 官方 Playwright 示例](https://github.com/e2b-dev/e2b-cookbook/blob/main/examples/playwright-in-e2b/README.md)

**官方事实：** E2B 声明每个沙箱运行在独立 Firecracker microVM 中，具有独立内核，不与其他客户共享内存或文件系统。[E2B：Security](https://e2b.dev/security)

**官方事实：** SDK 支持显式设置/修改沙箱超时和主动 `kill`；生命周期也支持超时暂停，因此「到时销毁」与「暂停保留」需要按实际配置区分。[E2B：Sandbox lifecycle](https://docs.e2b.dev/sandbox)

**实施判断：** 预制含 Node、执行器、已发布模块依赖和 Chromium 的镜像，可减少每次重复安装。公网任务的文件操作、shell、npm 与游戏浏览器执行应落在受控的隔离环境，避免只隔离构建却让代理在业务服务器上改文件/执行命令。worker 控制总时限、最大重试、并发、产物上传与沙箱销毁；平台管理密钥不进入沙箱。独立 VM 不会替代应用自己的网络策略、凭证权限和用量限制。

需验证生成执行器与模块能否在该镜像内完成生成、构建、截图及产物回传；现有项目尚未完成该适配。

### 试玩与主站隔离

**官方事实：** MDN 说明 `sandbox` 默认施加限制，属性 token 按需解除。缺少 `allow-same-origin` 时，内容使用特殊 origin，可能失去存储/cookie 等能力；同源内容同时获得 `allow-scripts` 和 `allow-same-origin` 时可移除 sandbox。MDN 还指出用户直接打开框架内容时可能脱离 iframe 限制，因此内容也应从独立 origin 提供。[MDN：iframe sandbox](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe#sandbox)

**实施判断：** 主站账户页面与生成游戏分开 origin，游戏域名不承载主站登录态。游戏仅按需要开启脚本、全屏或鼠标锁定等能力；不要默认授予弹窗、顶层导航、表单或下载权限。先验证 ES module、纹理加载、音频、键盘输入和存档需求，再确定 iframe 权限；不能把「一律禁止同源能力」当作无需验收的通用方案。如必须保留游戏自身 origin，应按游戏/版本隔离，避免不同用户作品共享存储与权限。

## 最小验证闭环（实施判断）

先从最小启动工程与少量模块完成一个原创组合玩法，连续跑通创建、试玩、修改、版本恢复与分享。再让同一个波次模块用于生存射击与塔防两个不同项目，证明模块能跨玩法组合，而不是复制两个整套模板。固定素材用于第一轮验收。

记录真实耗时、首次可玩率、修改回归率、重试次数和资源消耗，再决定开放范围。模块化首轮验收不要求同时实现 3D、多人服务器或插件市场；这些能力可以通过新模块和运行环境扩展，不由游戏类型枚举封死。

## 最小产品与代码边界

首版页面为创作入口、创作工作台、我的作品、公开试玩页。工作台以试玩为主要区域，同时提供对话与任务进度；保留停止任务、再试一次、版本恢复和发布到自有平台。用户不用选择模型、游戏分类或模块。自有平台首轮商业化增加开发者商品设置与收益记录、玩家购买和已购权益入口。外部平台发布、代码编辑器、社区互动及开发者生成服务收费分阶段补充。

在现有 `packages/*` 工作区下新增以下模块，路径是实施建议，尚未创建：

- `packages/web`：Next.js 页面、鉴权、项目与任务 API；页面轮询任务状态，后续再接实时事件。
- `packages/platform-worker`：领取任务、准备隔离工作区、控制并发与执行预算、保存 Git 提交和产物，执行自有平台发布并登记结果。
- `packages/game-runner`：封装能力规划、上下文恢复、Codex 执行、新建/编辑流程、构建和浏览器验收，向调度端返回结构化结果。
- `packages/game-modules`：管理模块清单、接口、实现、示例、验证及准确版本；先保留在同一代码库中。
- `packages/game-standards`：管理公共规范、适用范围、证据与候选、验证样例、版本发布和按需加载。初期用受 Git 管理的规则文件与验证脚本，复用 worker 执行维护任务。
- `packages/game-commerce`：封装商品、订单、链上付款核验、权益发放、退款对账和开发者收益记录；首轮接一个稳定币与一个网络，向游戏提供受控购买与权益查询接口。

首批业务数据包括 `projects`、`game_versions`、`generation_jobs`、`job_attempts`、`job_events`、`messages`、`usage_events` 和独立的 `releases`。项目记录私有仓库位置与最近可玩版本。每个游戏版本记录 Git 提交、运行环境、模块清单、规范快照、素材清单、构建产物、封面与验证结果；保存阶段记录待完成状态以便中断恢复。发布记录关联目标、来源版本、产物、状态与入口；首版只保存自有平台发布，后续允许各平台分别上线不同版本。发布更新目标的版本引用，避免覆盖正在被访问的文件。

首轮商业化增加商品、订单、支付请求、链上交易与事件、确认状态、扫描进度、发货凭证、玩家权益、退款与交易流水记录；多开发者场景再关联已验证收款钱包和服务费记录。交易数据保存在受权限控制的业务数据库，与项目代码 Git 历史分开。到账核验使用只读链访问，资金签名由对应钱包完成；生成工作区与公共规范库均不接收资金私钥或玩家付款信息。

第二种发布目标验证通过后，可提取 `packages/game-publishing`，集中处理适配器选择、发布任务与状态查询；各适配器声明实际支持的导出、预览、上传、提交、上线和回退操作。该包属于后续扩展，第一版不创建空实现。

公共规范闭环增加任务经验记录、候选改进和规范发布索引。经验保留访问范围与来源，公共规则只引用可共享证据。生成任务记录所用规范版本和规则清单，发布索引关联不可变规则内容、验证结果和被替代版本，初期无需另建知识图谱或向量数据库。

订阅验证阶段记录任务耗时、调用用量、额度错误和运行资源占用，不将订阅调用虚构成按 token 的 API 账单。公网 API 阶段再增加生成、素材、重试和沙箱的成本记录、额度预留与结算；任务重试和重复回调需要幂等。

## 推荐实施顺序与验收

模块拆分和 Codex 接入改变了原先固定模板方案的工作量。先完成两个可运行样例，再依据依赖改造与验收结果估算剩余工期。

| 阶段                 | 必须得到的结果                                                                                                                                               |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 单一执行器与最小工程 | Codex 接收任务、返回进度，在受控工作区生成并修改一个可玩游戏。                                                                                               |
| 公共规范最小闭环     | 首个任务加载有版本的基础规范并记录经验；从实际问题形成一条候选，经复现和回归验证发布，另一个项目的后续任务采用，已发布游戏保持原版本。                       |
| 验证模块组合         | 拆出少量真实需要的模块，完成组合玩法；同一模块在两个不同玩法项目中通过验收，缺少能力时能新增项目实现。                                                       |
| 网页与项目闭环       | 输入需求、排队、试玩、独立 Git、项目记忆、修改、版本恢复，以及发布到自有平台并分享连续走通。                                                                 |
| 公网内测准备         | 服务端生成接入、鉴权、执行隔离、任务恢复、取消、限额、失败回退与移动端输入通过验收。                                                                         |
| 自有平台玩家付费     | 面向海外玩家，先用一个稳定币与一个测试网络验证游戏买断和永久商品，打通订单归属、到账核验、发货、退款与卖方收入记录；技术验收和实际运营条件确认后再启用主网。 |
| 扩大共同改进范围     | 所有开发任务持续贡献经验，规范覆盖更多能力和运行环境；按真实需求抽取公共模块，发布前验证，跟踪采用效果并能撤回有问题的推荐版本。                             |
| 后续多平台扩展       | 根据需求逐个接入 Steam、微信小游戏、Roblox 等目标，完成目标环境试玩、发布准备和实际状态核验；上传与上线分别验收，各平台版本独立。                            |

内测前用固定样例覆盖模块单独使用、跨模块组合及常见修改（角色替换、速度/难度、增加敌人、换背景）。分别记录首次可玩率、修改回归率、较慢任务耗时与资源消耗。每个代表性玩法都应实际试玩，构建和截图通过不能替代玩法验收。
