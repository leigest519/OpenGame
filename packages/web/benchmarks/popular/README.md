# 热门小游戏能力实测（2026-10-15）

本轮使用部署在 `studio.xiajuan.app` 的真实创作 API、Codex 生成器、每项目隔离容器、版本保存与发布流程。选择依据与原作来源见 [研究记录](../../../../docs/developers/popular-minigame-benchmarks-2026-10.md)。仅借鉴公开核心玩法，游戏采用原创名称、几何图形和代码，没有提供原作源码或素材。

本轮是有明确规则说明和人工验收的生成测试，不能解释为“一句话全自动复刻商业游戏”。所有修改和修复均重新通过平台提交，没有在平台之外手写游戏后冒充生成结果。

## 本轮暴露的问题

1. **场景生命周期错误没有被自动修复。** 穿行失败任务的 `new Phaser.Game(...)` 后立即访问 `scene.events.once`，场景尚未启动时 `events` 不存在。原工作区在同一个平台容器检查中再次得到 `Cannot read properties of undefined (reading 'once')`。反馈具体位置后，生成器将监听移到 `create()`，加入就绪保护；同一启动/重开检查通过，随后完成真实撞车与重开。失败任务仍保留，未伪造成功状态。
2. **启动检查不能替代尺寸验收。** 方块v2在373×442容器中，棋盘底部452、手牌502–570、内容总高826像素，核心操作被裁剪。宽屏和启动检查均不能发现此缺陷。通过单独需求生成v3，按可用宽、高分配空间，预留手牌和控制区，说明可以折叠。相同373×442容器中，棋盘约189像素见方、底部290，手牌底部376，所有操作均在可视区；实际消行与撤销通过。规则模块与配置逐字节未变，避免布局修复改变玩法。
3. **长时间资源回收仍需专项测试。** 穿行目前累积道路数据，没有回收远处路段；500行数值检查通过并不证明长局内存稳定。本轮没有做多人并发、帧率压测、真机触摸、支付或商业留存验证。

## 知识沉淀

平台已为成功版本保存项目记忆和 `learning.json`，本轮检查到模型归纳经验处于 `observation` 状态；这不是自动批准的公共规范。建议将以下有证据的结论作为公共规范候选：

- Phaser场景事件与清理在就绪的生命周期内注册；外部按钮确认场景就绪后调用。
- 棋盘类游戏同时按宽、高分配空间；尺寸检查必须覆盖手牌、分数和重开等真实操作目标，而不只检查canvas存在。
- 网格清除先收集所有满行满列，再按并集清格；死局遍历全部剩余手牌。
- 撤销保存业务状态和随机数状态，撤销次数独立消费，非法输入不覆盖有效快照。
- 合成采用消费集合避免同一球重复参与；危险线计时区分新球保护、短暂越线与持续越线。

纯规则测试、浏览器操作证据与失败复现应随规范候选一起保留。三个样本不足以证明“支持任意游戏类型”，也不足以证明共享经验已改善后续成功率。

## 固定回归套件

`fixtures/` 保存本轮审阅后的三个规则样例及配置，共7个文件。方块采用v3：其规则和配置与已验收的v2逐字节相同。`manifest.json` 固定来源提交、文件散列、检查器散列与全部27个用例名称；少运行一个用例也不能作为完整通过。

平台的能力升级页调用 `src/server/evolution-regression.ts`，将每个样例与可信检查器复制到独立只读、离线容器中执行。本机与服务器使用相同入口，无需安装新依赖或调用生成模型。运行 `npm run evolution:check --workspace=@opengame/web` 可单独检查执行环境。

该套件是公共经验发布的参照规则回归门槛。候选文本由维护者独立审核，固定样例不会受文本影响，因此不得将套件通过称为“新规范提升了生成质量”。新游戏对照生成、视觉、触屏和长时性能仍是后续独立评估项目。
