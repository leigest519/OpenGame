# 生成质量流程基准

在 `packages/web` 执行 `node --import tsx benchmarks/quality/run.ts`，使用 Astra 和固定的“乐高风格 2D 塔防”需求。命令后可附另一条需求。需要已登录的 Codex CLI、Docker 和已准备的当前运行镜像；会实际调用模型并消耗额度，不属于普通单元测试。

运行使用 `output/game-quality-*` 中新建的独立数据目录，不连接工作台数据库或修改已有项目。沿用实际平台的项目准备、基础知识选择、规范、受限生成器、只读规划/评审和容器验收。缺少计划时先形成约定，然后按片段、验收、扩充、复验推进，整体受 Astra 任务时限约束。

结果包含每次调用的提示词与回复、只读/写入类型及耗时、截图、冻结验收场景及结果、最终静态游戏、工作目录和模型用量；失败保留 `failure.json` 和已完成证据。工作区的 `.opengame-context/quality-review` 另保留每次检查的源码和可玩检查点。实际模型 ID 记录为 requestedModel，推理档位当前使用提供方默认并明确记为未知，不能宣称与旧样本完全相同设置。

单次样本只验证管线能否工作及暴露缺陷，不是成功率或质量提升的统计对比。基准绕过聊天/账号/数据库/发布，调用的是实际游戏制作流程。配对试验方案见 [管线设计](../../../../docs/developers/game-production-pipeline-design-2026-10-23.md)。

为诊断中断后的内容，可加 `--continue game-quality-目录名`。它将该目录中的未完成源码及原制作约定复制到新的独立目录，重新检查全部验收点，最多十分钟；不改来源，也不继承来源的通过结论。结果明确标为 `unfinished-source-continuation`，保存复制文件哈希和来源，不能计作从零生成成功或覆盖原失败样本。自定义需求续跑时应同时传入原需求。旧场景只保留在来源证据中，续跑依照原约定重新审查用例；若修正了用例，须记录原因，不把它声称为原冻结场景通过。
