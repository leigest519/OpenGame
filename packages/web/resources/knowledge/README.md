# 游戏知识库

本地已有游戏为平台提供初始知识。每次制作按当前需求选取经验，完成后继续积累，使新游戏能够利用此前的设计、模块和验证成果。

## 当前流程

1. `seed.json` 保存首批经整理的经验，来自本地塔防项目和《虾了吗》规则及试玩验证。每条包含适用条件、做法、易错点、来源和实际验证范围；可附带公共模块入口。
2. worker 按当前需求中的能力关键词检索。修改游戏时还参考游戏名，并排除当前项目已贡献的条目，因为当前项目自己的源码与记忆会单独提供。通用容器经验保留为基础参考。
3. 每次最多选取 5 条，条目 JSON 总长度不超过 6,000 字符。初版采用关键词匹配，没有向量检索或模型训练。
4. 选中内容进入生成提示词，同时写入 `knowledge.lock.json`，包括来源、内容与校验值。平台在保存版本前重新写入原快照，防止生成器改写来源。基础游戏版本恢复不改变已发布游戏或公共经验。
5. 生成器通过 `learning.json` 提交本轮至多 3 条通用经验。每次新任务先清空这份文件，避免旧经验被当成本轮新结论。没有新经验可以留下空数组。
6. 通过平台检查并完成版本保存后，经验与版本在同一个数据库事务中归档。取消、失败和未完成保存的任务不会贡献可复用条目；重复保存不会重复归档。
7. 后续游戏可以检索这些项目经验。它们标记为“待复验”，并附平台实际完成的构建、启动和重开检查范围。相同内容去重，检索最近 200 次有经验的成功任务。本机模式可复用本地所有项目经验；受邀模式仅可复用本人的经验。跨成员经验必须来自当前已发布的公共知识快照，单独将旧经验状态改成 `approved` 不再产生共享权限。

## 边界

知识库内容是参考材料，不能提升执行权限，也不能覆盖当前需求与固定制作规范。模型提供的 JSON 不能指定来源、验证级别或稳定状态。内容不是整个项目源码、对话或私有素材的副本。

基础经验、待复验的项目经验、已发布公共经验和稳定规范是不同层次。新经验可以立即为本人后续设计提供参考。公共知识已有独立的审核、回归、发布和回退流程；自动提取公共代码模块、修改平台源码和验证生成成功率提升仍未实现，固定制作规范当前为 0.3.0，由平台显式升级。公共知识版本不会提高经验的指令权限，也不能覆盖用户需求。

首批入库由人工整理完成；首版不自动扫描磁盘上的所有仓库。之后平台生成的游戏会使用上述经验归档流程。旧游戏版本没有知识快照或 `learning.json` 时，不补造历史记录。

## 检查与查看

打开工作台顶部的“知识库”，可以查看来源与验证范围，并用一句需求预览会选取哪些经验。预览不会调用模型或开始制作。

`test/knowledge.test.ts` 验证选取范围、上下文预算、快照、结构化经验限制和提示词接入。`test/integration/store.test.ts` 验证成功版本入库、跨项目再选取、幂等保存以及失败和取消任务隔离；测试使用独立临时数据库。

## 公共能力升级（首版）

入口为 `/evolution`，也可从知识库进入。流程如下：

1. 成员选择自己的项目经验，编辑为通用做法并明确同意贡献。仅提交被选择的经验与来源给维护者；其余私人经验不会进入审核队列。
2. 维护者审核来源、适用范围、通用性和私人信息，记录依据。候选内容不可原地更改；修改需要提交新候选。模型无法自行指定审核结果、来源或验证级别。
3. 选择已审核候选创建版本，合并当前公共经验。版本保存不可变的条目快照、内容散列、基准套件散列和基础公共版本。
4. 现有串行 worker 在制作任务空闲时自动复验。三个固定样例分别执行12、7、8组纯规则检查，总计27组。源码配置与检查器散列写入 `benchmarks/popular/manifest.json`，任何改变都需要重新登记套件。
5. 每个样例在独立的离线、只读、非root容器里运行；不执行候选文字、不读取真实项目、凭证或对话，也不调用模型或消耗创作额度。全部测试及完整报告通过后，维护者才可发布。新发布要求证据未超过24小时、套件未变化、基础公共版本仍一致。
6. 发布后所有受邀成员按需检索该版本的通用经验；公开数据不包含来源私人项目的名称、ID、源码或对话。每条选中的公共经验附带发布编号，随游戏知识快照进入Git。
7. 可以回退到历史已发布版本或只使用基础知识。发布和回退采用预期版本校验，防止并发覆盖；不改变任何已有游戏及其历史快照。进程中断会将未完成复验标为失败，绝不默认为通过。

受邀环境通过服务端 `OPENGAME_KNOWLEDGE_REVIEWERS` 配置已有成员UUID（逗号分隔），默认无人拥有审核发布权限。本机模式可维护本机知识。API每次检查权限，隐藏按钮不作为授权边界。

**证据边界：**固定样例回放证明该套件仍符合既定规则，不证明候选文本能改善新游戏生成；不是浏览器、真机或画面测试。后续应增加同模型、同预算、含未见题目的生成对照评估，再以首次成功率、缺陷数、耗时与成本衡量进步。不能仅因归档了更多经验就宣称平台已变强。

`test/evolution.test.ts` 检查散列稳定性与缺失/重复用例不能发布；`test/integration/evolution.test.ts` 使用临时数据库验证贡献归属、审核权限、幂等提交、发布门槛、隐私、竞争发布、中断恢复、证据时效及回退。集成测试的报告是显式合成的流程夹具，不作为游戏测试成绩。

`npm run evolution:check --workspace=@opengame/web` 实际运行同一套Docker检查器，脱敏结果写入数据目录的 `evolution-verification.json`。线上版本的正式复验证据保存在 `studio_knowledge_releases.report`，审核与切换记录保存在 `studio_evolution_events`。
